  <behavior>
    - while a holder process keeps .epb/lock, `epb init --wait 1 --json` on that case exits 4 LOCK_TIMEOUT within 5 seconds, its message names the holder's command, and no file changes
    - while the lock is held, `epb status --json` exits 0 within 5 seconds
    - when the holder releases after about 2 seconds, `epb init --wait 20 --json` waits, then exits 0, taking at least 1.5 seconds
    - when the holder is killed with SIGKILL, the next mutating command gets the lock at once
    - the lock file holds JSON with pid, command and started, and no host name
    - the parser default for --wait is 60.0
  </behavior>
  <action>
    `epb/lock.py`: `LOCK_FILE = ".epb/lock"`; `acquire(path, *, wait_s, command, poll_s=0.2) -> LockHandle` opens the file with `os.open(path, os.O_RDWR | os.O_CREAT, 0o644)` and polls a non-blocking lock until the deadline: `fcntl.flock(fd, LOCK_EX | LOCK_NB)` on POSIX, `os.lseek(fd, 0, 0)` then `msvcrt.locking(fd, LK_NBLCK, 1)` on Windows (untested here, A10). On success truncate and write `{"pid", "command", "started"}` as JSON (no host name; host names often contain a person's name). On timeout read the holder's JSON best-effort and raise `EpbError("LOCK_TIMEOUT", "Another epb command (<command>, started <time>) is still changing this case folder.", hint="Wait for it to finish, then try again. The lock is released automatically when that command stops.")`. `LockHandle.release()` unlocks and closes; it is also a context manager. Never check whether a PID is alive and never call `os.kill`.
    `epb/workspace.py`: `open_for_init` and `open_for_mutation` acquire the lock with `ctx.wait` and the command name before `txn.recover`, and release it on exit. `open_read_only` takes no lock.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-31 | Denial of service | lock.acquire | medium | mitigate | OS advisory lock released on process death, bounded wait with exit 4 LOCK_TIMEOUT naming the holder; no stale-lock heuristics |
